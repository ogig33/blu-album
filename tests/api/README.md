# BluAlbum – API tests

Contract tests for every player request the app uses and for the endpoints of the API reference [`docs/bluos-api.md`](../../docs/bluos-api.md), against the real player. They check the **structure** of the answers (elements, attributes), not concrete albums or numbers. Node.js only (`node:test`, `fetch`, `node:assert`), no npm packages, nothing to install. They also record the player answers (`fixtures/`) that the UI tests use in sanitized form.

**Only against your own player.** `read.test.js` only reads. `write.test.js` interrupts playback and changes settings, favourites, playlists and the player name for a moment; it restores everything and checks that at the end. `manual.test.js` (reboot, rescan, rebuild index, firmware upgrade …) sends nothing unless asked for request by request.

## Setup
- Node.js 20 or newer.
- The player: `PLAYER=<IP address>` before each command, or a file `config.json` here: `{ "host": "<IP address>" }`. Further keys: `saveFixtures` (default `true`: answers to `fixtures/`), `runManual` (default `false`). The environment variables `PLAYER`, `SAVE_FIXTURES`, `RUN_MANUAL` override the file. `config.json` and `fixtures/` are git-ignored: the answers contain details of your network and library.

## Before a run
- A queue with at least 2 entries, playing or paused (not a radio stream).
- At least one preset.
- A USB drive is optional; USB requests are skipped without one.
- Optional: at least one favourite song and more than 10 queue entries; W17 and W21 are skipped otherwise.

## Run
In this folder (or with the path, e.g. `PLAYER=192.168.1.20 node --test tests/api/read.test.js` from the repository root); the commands assume `config.json`:

| Command | Runs | Effect on the player |
|---|---|---|
| `node --test read.test.js` | folder 1: A, E, V, about 40 s | none |
| `node --test write.test.js` | the app reads (A), then folder 2: C, W, S, about 70 s | playback is interrupted; everything is restored |
| `RUN_MANUAL=1 node --test --test-name-pattern="^M01 " manual.test.js` | one manual request (here the doorbell) | see "3 Manual" |
| `node --test --test-name-pattern="^A19 " read.test.js` | one request (requests that need keys of earlier ones are skipped) | |
| `PLAYER=192.168.1.20 node --test read.test.js` | against another player | |
| `node --test --test-reporter=junit --test-reporter-destination=report.xml read.test.js` | JUnit report | |

Never run two test files in one command (`node --test` runs files in parallel).

After a firmware update: run `read.test.js` and `write.test.js`, compare `fixtures/23-api-version.xml` and `fixtures/24-bluos-version.xml` with the versions in the reference and look at the failed tests.

## Structure
- `lib/player.js` – configuration, requests (`send`, `http` with the axios options the scripts use), `save()` for fixtures, `dec` / `attr`, `expect()` (chai style: `expect(x).to.equal(y)`), `request(name, { method, url, headers, form, multipart, pre, post, tests })`.
- `lib/state.js` – the snapshot of the player state for `write.test.js`.
- `read/`, `write/`, `manual/` – the requests, one module per group, loaded in order by the test file; values pass from one request to the next through `vars`, so a test file runs in one process.
- Loading a module (`require`, `node -e`) already runs its requests against the player (`node:test` starts every registered test); check a file with `node --check` only.
- Each request is one test: `pre(req)` may set `req.url`, `req.headers`, `req.body` or call `req.skip()`; `post(req, res)` saves fixtures and stores values in `vars`; `tests(req, res, test)` checks, each `test(name, fn)` is a subtest that runs at once.
- Every request sends `Accept-Language: en` (as the app) unless it sets its own. URLs are built with `encodeURIComponent` by the scripts and sent as they are.
- `fetch` gives no body for HTTP 204, 205 and 304 (Fetch standard); `/alsa_setting` answers 205 with a body of one space, which the fixture therefore leaves out.
- Every request has a unique prefix: **A** app reads, **E** album details / new variants, **V** reference reads (folder 1); **C** app commands, **W** queue and playback, **S** settings and playlists (folder 2); **M** manual (folder 3). Fixture files of the app requests keep the number without the letter (`A19 Status` → `19-status.xml`).

## 2 Write (changes the player) – `write.test.js`
Runs A01–A30 first, then the folders below in this order. Playback is interrupted; queue, position, pause state, volume, repeat, favourite and every changed setting are restored, test playlists deleted. Two tests at the end:
- "Queue position and play state as before the run" plays the queue entry and position of the start again and pauses if the player did not play (C44 loads the queue from a playlist and leaves it at entry 0).
- "Player state as before the run" compares a snapshot taken before the first request (`lib/state.js`: status, name, queue, settings `player` and `audio`, listening mode, playlists, presets, favourite albums, songs, artists) with one after the last; both go to `fixtures/state-*-write.json`. A failed subtest names the value that was not restored.

The requests:
- **C01–C47** (commands): every command the app uses: favourite, play album, pause, resume, skip, back, play queue entry, seek, add to queue, remove from queue, shuffle on / off, repeat (queue / track / off), volume (level, ±dB), clear, save / load / delete playlist. The queue is saved as `__bluos_album_player_test__` at the start and loaded again at the end; favourite, repeat and volume are restored, the test playlist is deleted. It also checks that the playlist id (`/Playlist` id = `<pid>` of `/Status`) changes after add, remove, shuffle on / off, clear and load – the app reloads the queue only on this change. The favourite and album commands (C05–C09, C22–C25) use the album of A07 and A09.
- **W01–W15**: moves the first queue entry and back (`/Move`), stops (`/Stop`), loads the next preset (`/Preset?id=+1`), skips on the radio station if it offers a skip action (`/Action`), returns to the former queue entry and position (`/Play?seek=…&id=…`), pauses again if it was not playing and restores the volume.
- **S01–S35, S41–S52**: reads a setting, changes it, checks the new value and restores it: indicator brightness (`/setting`), replay gain (`/audiomodes`), balance (`/alsa_setting`), trim of a fixed group member (`/SlaveVolume`, skipped without a fixed group). Reads through `/proxyToSlave`, the playlist backup `/download_playlists_api`, `/redirectToCp`, the web pages `/wificfg` and `/triggercfg` and `/Info?infourl=…` (only when the playing item has an info URL). Saves the queue as test playlist `__bluos_verify__`, adds an album with `/AddToPlaylist` and deletes the playlist; renames the player with `/Name?set=` and back (S31–S35); switches the listening mode (`/alsa_setting?preset=`), checks with a `/Status` long poll whether the etag reports it, and back (S41–S47); checks whether `/Shuffle` without `state` switches shuffle off, and restores it (S48–S52).
- **W16–W29** (after S52): parameters of `/Add`, `/AddFavourite` and `/DeleteFavourite` found by `private/tools/crawl-endpoints.js`. W16 saves the queue as playlist `__bluos_verify_add__`. W17–W22 run the `autoplayURL` of the first favourite song (`category=FAVOURITES`), of a song of the first composer (`composer=`) and of the first song on the second page of the saved queue playlist (`offset=`, skipped with 10 queue entries or fewer) and check with `/Status` that this song plays. W23–W26 favourite a composer song that is no favourite yet with the `/AddFavourite?fn=…` of its context menu, find it in the favourite songs, remove it with `/DeleteFavourite?fn=…` from that list's menu and check that it is gone. W27–W29 load the saved queue, return to the former entry and position, pause again if it was not playing and delete the playlist. Every URL comes from `/Browse`; skipped when the player does not play from the queue. Answers go to `fixtures/verify-add-*.xml` and `fixtures/verify-*-favourite-song.xml`.
- **W30–W33** (independent of W16): favourite the first library artist that is no favourite yet with the `/AddFavourite?artist=…` of its context menu, find it in the favourite artists (Library › Favourites › Artists), remove it with `/DeleteFavourite?artist=…` from that list's menu and check that it is gone. Answers go to `fixtures/verify-*-favourite-artist.xml`.
- **W34–W37** (independent of W16): move queue entry 0 to position 3 (`/Move?new=3&old=0`), check the order (entry 0 taken out and inserted at index 3, a new queue `id`), move it back (`/Move?new=0&old=3`) and check that the order is as before. Skipped with fewer than 5 or more than 200 queue entries.
- **W38** (independent of W16): favourite the first library playlist that is no favourite with the `/AddFavourite?playlistid=…` of its context menu, find it in `category=FAVOURITES`, read the menu with `&isFavourite=1` appended to the key (as the app does), remove it with its `/DeleteFavourite?playlistid=…` and check the menu offers `favourite-add` again. Skipped without a library playlist.
- **W39** (independent of W16): is `mid` of `/Status` the library version? Checks `mid` = root `id` of `/library/v1`; favourites the first library album that is no favourite with the `/AddFavourite` of its context menu and removes it again with `/DeleteFavourite` (menu key with `&isFavourite=1`), each time with a long poll on `/Status` open: `mid` changes with the library id and the long poll answers within 5 s. Skipped without a library album that is no favourite.

## 3 Manual (run on purpose) – `manual.test.js`
Every request is skipped unless `runManual` is set, also when it runs on its own. Run single requests: `RUN_MANUAL=1 node --test --test-name-pattern="^M0[1-3] " manual.test.js`; leave `runManual` in `config.json` at `false`.
- **M01**: doorbell chime (`/Doorbell`; players without a chime answer `Not supported`).
- **M02–M03**: library rescan (`/Reindex`); it runs in the background for minutes.
- **M04–M06**: stores a test preset `__bluos_verify__` (`/SetPreset`). No request to delete a preset is known – remove it in the BluOS app.
- **M07–M08**: soft reboot (`POST` to port 80 `/reboot`), then waits until `/SyncStatus` answers again (at most 5 minutes) and logs how long the restart took.
- **M09–M12**: saves a backup of the playlists (`/download_playlists_api`, to `fixtures/verify-playlists-backup.json`), uploads the same backup again (`/upload_playlists_api`) and checks that the playlists are unchanged. Needs `saveFixtures`; the upload is skipped without a fresh backup.
- **M13**: clears the recent stations (`/ui/clearUsageHistory?stations=1`) – the history is lost.
- **M14–M18**: switches the statistics collection (`/statistics?enable=0|1`, port 80) and back, read from the diagnostics page. While it is on, the player may send usage statistics to Bluesound.
- **M19–M20**: rebuild index (`/delete_index`, port 80) – the library index is deleted and the whole library is scanned again; then `/Status`.
- **M21**: `/UpdateDNS` (answers empty, no visible effect; purpose not known).
- **M22**: `/RadioAddPreset` adds TuneIn station s16252 as URL favourite `__bluos_verify__`; M24–M26 remove it again.
- **M23**: `POST :80/playurl` plays TuneIn station s16252.
- **M24–M26**: find every `__bluos_verify__` in the TuneIn favourites (category "Url", `preset_id` `u…`; also copies left by earlier runs), remove them with the `/DeleteFavourite?id=u…&service=TuneIn` of their context menu and check that none is left.
- **M27–M30**: favourite the first local TuneIn station that is no favourite (`/AddFavourite?preset_id=…` from its context menu), find it in the TuneIn favourites, remove it with `/DeleteFavourite?id=…` and check that it is gone. The favourites are stored in the player's TuneIn account.
- **M31–M34**: the same for the first station of Radio › Most popular stations (Airable): `/AddFavourite?service=Airable&url=…`, the station is marked `is_preset=1` in the list, `/DeleteFavourite?…&url=…` removes it. Without a login to the radio service the player answers `Login to use favourites`; M32–M34 are skipped then. Answers go to `fixtures/verify-*-favourite-{url,tunein,airable}.xml`.
- **M35–M38**: firmware upgrade, only when one is available. M35 remembers the BluOS version and reads the notification of `/update`; without one it first checks for an upgrade (`/upgrade?noheader=1`, Help › Check for upgrade); M36 sends the url of the notification's button that is not the delay ("I want it now", `/upgrade?upgrade=all`), skipped without one; M37 asks `/update` and `/GitVersion` every 3 s and logs every change until the player answers with another version (at most 30 minutes, stops after 5 minutes without a change); M38 keeps the upgrade lines of `/Dataexport` and the versions of every player of the group. Answers go to `fixtures/verify-upgrade-*`.
- **M39–M41**: does the root attribute `id` of the `/library/v1` answers change with the library? M39 remembers the id, the album count of the index and the newest album (`fixtures/verify-library-id.json`); M40 reads them again and logs what changed (run it after each change, e.g. a favourite, a new album on the share); M41 starts a rescan (`/Reindex`) and logs every change of these values and of `indexing` and `mid` in `/Status` every 5 s until 90 s after the last change (at most 15 minutes, `fixtures/verify-library-id-reindex.txt`); it checks that `indexing` counted the files and that the id changed after the rescan.
- **M42**: pink noise (`/PlayTestSound?sound=1&volume=20&type=pinknoise`, as the BluOS app plays it while pairing speakers), stopped after 3 s with `sound=0&volume=20`; logs `/Status` before, during and after (the playback stops) and checks that the volume is unchanged.
- **M43**: `/SetInitialized` on a player that is set up already; `initialized` of `/SyncStatus` must stay the same.
- **M44**: `/SetMaster` with `Accept: text/javascript`, as the BluOS app sends it; logs the answer root and checks that the grouping of `/SyncStatus` is unchanged.
- **M45**: removes test shares left over by an earlier run, adds the test share `\\127.0.0.1\blualbum-test` (the player's own address without an SMB server, user `guest`, no password) with `POST :80/AddShare` and removes it with `POST :80/RemoveShare`. The mount fails: `AddShare` answers `Addshare failed` only after several minutes and stores nothing, `RemoveShare` answers `Share not found`; `/Shares` must be as before. No `/Reindex`.
- M42–M45 write their results to `fixtures/verify-{playtestsound,setinitialized,setmaster,addshare}.json`.

## Fixtures
With `saveFixtures` every request stores its answer in `fixtures/` (git-ignored): the answers contain details of your network and library (IP addresses, share names, room name). V12 writes the settings tree to `settings/`; the owner's private API tools add `wordlist/` and `crawl-endpoints.json`.

To use them for the UI tests, copy them without personal details (from the repository root; only `NN-*.xml`, IP addresses, room name, share and mount paths and USB drive ids replaced):

```
node tests/api/sanitize-fixtures.js
```

Then run the UI tests (`npm test` in `tests/ui`): a library with other albums gives other fixtures, and some UI tests expect certain content (see "Update the fixtures" in [`tests/ui/README.md`](../ui/README.md#update-the-fixtures)).

`23-api-version.xml` and `24-bluos-version.xml` record which player software the answers come from (API version from `/Version`, BluOS version from `/GitVersion`).
